# Create or refresh a Continuity design board

**Optional, on demand.** General Continuity initialization does not authorize board creation. Use this reusable prompt now only when the user explicitly requests a board and a suitable reference/design direction exists, or return to it later. The starter includes the same prompt at `continuity/design/initialize-board.md`: tell the agent "Read continuity/design/initialize-board.md and initialize the design board using [reference]." Keep that installed prompt for later use; it is not temporary initialization material. This request authorizes design documentation and board artifacts, not product changes or dependency installation.

---

Confirm an explicit request to create/refresh the board exists; discovering or reading this prompt alone is not authorization. A user request to execute this prompt is sufficient; do not ask again. Read applicable instructions, Continuity's contract/status/complete map, and `continuity/design/README.md`. Read the accepted design language and relevant existing board entries, then inspect actual token definitions/accessors, reusable components, and representative accepted screens. Read Aurora/TokenSeed integration details only if the project actually uses them; neither tool is required. If there is no UI, explain that a board is not applicable. If no useful accepted screen, supplied reference or sufficiently established visual direction exists, recommend deferring, record the gap and stop before generating costly visual artifacts. Ask for the missing reference only when the user wants to proceed now. Preserve existing references and assets. Deferral does not make general Continuity initialization incomplete.

Create or refresh a focused local visual study in `continuity/design/boards/<topic>/`, or preserve an existing board's location and index it. Favor a viewable HTML/CSS board with relevant locally available fonts/assets, a short README, anchored sections and a preview where supported. Use the project's own semantic roles and primitives as the reference; if HTML approximates native components, label the difference. Inspect existing media before editing it, use available appropriate tools, and preserve licenses. Do not copy a different project's identity or introduce network/font dependencies merely to render a board.

Show the recognizable north-star compositions and reusable foundations: typography/hierarchy, colors with purposes, spacing/shape, actions, forms, cards and feedback where applicable. Include relevant light/dark appearances, narrow layouts, long content and interaction states. Use fictional content. Label the artifact as a design-language study, with its date, source/provenance and acceptance state; it does not define exact app screens, behavior, navigation or live data. Proposed departures remain in `planning/studies/` pending selection, rather than replacing accepted design rules.

Keep the short design-language Markdown sufficient to choose a pattern and link relevant board sections. Never require routine agents to load the full HTML, token export or all boards. Document how to open/serve the board and retain a static fallback if practical. Check file/asset links and visually inspect the output at relevant widths and appearances with available tools; report actual results and inaccessible/unverified states. Update design/planning indexes and source routes when changed. Record this turn's artifacts, human preview steps and expected result in the implementation log, retain pending checks in status, and follow handoff review. Do not commit or change production UI unless separately authorized.
